# Security

This document records the threat assumptions, the controls that are
implemented, and the gaps that were accepted and why.

## Threat assumptions

The service is internet facing and unauthenticated in this assignment, which
makes the realistic threats:

1. **Abuse of the public endpoint.** Automated traffic driving up compute and
   model cost, or denying service to real users.
2. **Prompt and query injection.** Hostile text in a query attempting to make
   the model act outside its purpose, or to surface content the requester
   should not see.
3. **Knowledge base poisoning.** Hostile content in an indexed document
   influencing answers for every user.
4. **Credential theft.** An attacker obtaining the database password or a
   cloud credential from the repository, an image, CI logs or state.
5. **Supply chain.** A vulnerable or malicious dependency or base image.
6. **Lateral movement.** A compromise of one workload being used to reach the
   database or another service.

Out of scope here, and called out rather than silently ignored: end user
authentication and tenant isolation. A real deployment would put identity in
front of the service and scope retrieval to the caller's permissions. That is
the single largest gap between this assignment and production.

## Controls

### Secrets

- No secret is committed. `.env` is git ignored; `.env.example` holds placeholders only.
- The database password is generated by Terraform, stored in Secret Manager and mounted by reference at runtime. It never enters an image or an environment file.
- CI authenticates to Google Cloud with Workload Identity Federation. There is no service account key in the repository, in GitHub secrets, or on disk anywhere.
- Trivy runs with the secret scanner enabled, so a committed credential fails the build rather than being found later.
- Terraform state contains the generated password. The state bucket is private, versioned, and readable only by the platform team and the deploy service account.

### Identity and access

- One service account per workload. The API can read one secret and connect to Cloud SQL; it cannot push images or read other secrets.
- The indexer has no inbound network path at all. It is a job, not a service.
- Public invocation is granted explicitly in Terraform rather than inherited, so making a service public is a visible, reviewable change.
- Cloud SQL IAM authentication is enabled as a database flag, which is the path to removing the password entirely.

### Network

- Cloud SQL has no public IP. It is reachable only over private IP from the VPC.
- Cloud Run reaches the database through Direct VPC egress restricted to private ranges.
- The VPC denies ingress by default. Postgres is allowed only from the subnet.
- Subnet flow logs are enabled for audit.

### Edge

- Cloud Armor in prod: per IP rate based banning, plus the preconfigured SQL injection and cross site scripting rule sets.
- An in-process fixed window rate limiter is the fallback, so the protection still exists when the service runs without the load balancer in front of it.
- Request bodies are bounded by the schema: a query is at most 2000 characters and `top_k` at most 20.

### Pipeline

- `ruff` and `pytest` gate every pull request.
- Trivy scans the filesystem for vulnerabilities, secrets and misconfiguration, and fails on high and critical findings.
- Trivy scans the built image **before** it is pushed, so a vulnerable image never reaches the registry where a deploy could select it.
- Images are tagged with both a version and the commit SHA. A deployed revision is always traceable to a commit.
- The default `GITHUB_TOKEN` is read only. `id-token: write` is granted only because federation requires it.
- Production deployment waits on a GitHub environment with a required reviewer.
- No value from an event payload is interpolated into a shell command. Inputs reach the shell through the environment, and the resolved image tag is pattern-checked before a deploy command can use it, so a tag carrying shell metacharacters fails the run instead of executing.
- Terraform plans on pull requests from forks are skipped, since GitHub withholds the id-token there; `validate`, which needs no credentials, still runs.
- Infrastructure is applied only by the `terraform` workflow. A daily drift check compares live infrastructure against `main` and opens an issue when they diverge, so a change made by hand in the console cannot quietly become the real configuration.

### Runtime

- Containers run as a non root user (uid 10001).
- Read only root filesystem, all capabilities dropped, `no-new-privileges` set in compose and matched by the Cloud Run defaults.
- Multi stage builds keep build tooling out of the runtime image.
- Structured logs carry a request id but never the query body, so logs do not become a copy of user input.

### AI specific

- The LLM provider is behind an interface and defaults to a mock, so no data leaves the platform in the default configuration.
- Prompts are built from retrieved chunks with a hard context budget. Retrieved text is placed in a labelled context block and the instruction tells the model to answer only from it. This reduces but does not eliminate prompt injection; the honest position is that a retrieval system that ingests untrusted documents cannot fully prevent it.
- The knowledge base is a reviewed directory in the repository, not a user upload path. Allowing user uploads would need content review before indexing.
- Token and cost counters are exported, and an unexpected climb is the earliest signal of abuse.

## Accepted gaps

| Gap | Why it was accepted |
| --- | --- |
| No end user authentication | The assignment specifies an open API. Identity in front of the service is the first thing a real deployment needs. |
| No per tenant retrieval scoping | Follows from the above. Retrieval would need to filter by the caller's permissions. |
| Password authentication to Postgres | IAM authentication is enabled at the database but wiring it through the application was out of scope for the timebox. |
| Cloud Armor only in prod | It requires a load balancer. Dev is reached directly so the pipeline can smoke test it. |
| No image signing or provenance attestation | Binary Authorization with signed attestations is the next step and is a day of work, not an hour. |
