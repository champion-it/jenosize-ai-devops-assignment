# Infrastructure

Terraform for the Jenie Helpdesk AI platform on Google Cloud.

## Layout

```
bootstrap/        APIs, state bucket, Artifact Registry, WIF, CI identities
modules/
  network/        VPC, subnet, private service access, firewall, Cloud Armor
  database/       Cloud SQL Postgres with pgvector, backups, DATABASE_URL secret
  service/        Cloud Run service and job, service accounts, scheduler
  observability/  alert policies, log bucket and sink, log based metrics
envs/
  dev/            small, single zone, scale to zero
  prod/           regional, warm instance, Cloud Armor, longer retention
```

Both environments call the same modules. They differ only in the values they
pass, which is what keeps dev a true rehearsal for prod.

## First run

Apply [`bootstrap/`](bootstrap/README.md) first. It enables the APIs, creates
the state bucket, the Artifact Registry repository, the Workload Identity
federation and the two CI service accounts. An environment apply fails
without it, because it cannot enable the APIs it needs in order to run.

```bash
cd bootstrap
cp terraform.tfvars.example terraform.tfvars
terraform init && terraform apply
terraform output github_repository_variables   # set these in the repository

cd ../envs/dev
cp backend.hcl.example backend.hcl             # bucket from the output above
cp terraform.tfvars.example terraform.tfvars
terraform init -backend-config=backend.hcl
terraform plan
terraform apply
```

## State

State is in a GCS bucket with object versioning enabled, one prefix per
environment. GCS provides state locking natively, so no separate lock table
is needed.

The bucket is created by [`bootstrap/`](bootstrap/README.md), not by the
environments. A configuration that holds its own state bucket cannot be
destroyed or recreated cleanly, so bootstrap keeps its state locally and the
environments keep theirs in the bucket it creates.

Recovery from corrupted state is `gsutil cp` of the previous object version
over the current one. Object versioning is what makes that possible, so it is
checked as part of the bootstrap.

## Secrets

No secret is written into a `.tf` file, a `.tfvars` file or an image.

The database password is generated by Terraform, stored in Secret Manager and
mounted into the containers at runtime by reference. It is present in
Terraform state, which is why the state bucket is private, versioned and
readable only by the platform team and the deploy service account.

A production hardening step beyond this assignment would be Cloud SQL IAM
authentication, which removes the password entirely. The database flag is
already enabled, so the change is additive.

## Change process

Infrastructure is not applied from a laptop. `.github/workflows/terraform.yml`
plans on every pull request that touches `infra/**` and posts the plan as a
comment, applies on merge to `main` behind a required reviewer, and runs
`terraform plan -detailed-exitcode` on a daily schedule. Exit code 2 on that
scheduled run means live infrastructure has diverged from the repository, and
the workflow opens a `drift` issue with the pending changes attached.

The commands below remain the way to bootstrap an environment for the first
time, and the way to investigate locally.

## Who owns what

The deploy pipeline owns the container image and the traffic split. Terraform
owns everything else. The Cloud Run resources carry `ignore_changes` on image
and traffic so that a `terraform apply` run after a deploy does not roll the
service back to the image recorded in state. Getting this boundary wrong is
the most common way an IaC setup and a CD pipeline fight each other.

## Backups and disaster recovery

| Scenario | Control | Recovery |
| --- | --- | --- |
| Accidental data deletion | Automated daily backups; point in time recovery in prod | Restore to a timestamp before the deletion. Prod RPO is minutes, dev is 24 hours. |
| Database instance loss | Regional availability in prod with a standby in a second zone | Automatic failover, no manual action. |
| Region loss | Backups replicated to a multi region location | Restore into a second region, then `terraform apply` with the new region. RTO measured in hours, which is the accepted trade for the cost of a hot standby. |
| Vector index corruption | The index is derived data, not source data | Rerun the indexer job against `/data`. It is idempotent and rebuilds from scratch with `--force`. |
| Bad release | Cloud Run retains previous revisions | Shift traffic back to the previous revision. Seconds, no rebuild. |
| Terraform state corruption | GCS object versioning | Restore the previous object version. |
| Project level loss | Out of scope for this assignment | Would need a second project and replicated backups, decided against here because the cost is not justified at this stage. |

Targets: prod RPO under 5 minutes and RTO under 1 hour; dev RPO 24 hours and
RTO best effort.

The restore procedure is only credible if it has been run. The intended
practice is a quarterly restore drill into a scratch instance, with the
measured restore time recorded.

## Cost notes

- Cloud Run scales to zero in dev, so an idle environment costs close to nothing.
- Prod keeps one warm instance. That is a deliberate spend to avoid a cold start on the first request.
- Cloud SQL is the floor on cost in both environments. A single shared instance with one database per environment would be cheaper; separate instances were chosen so a dev mistake cannot reach prod data.
- The default embedding provider runs on CPU inside the worker. No GPU is provisioned anywhere. If a hosted model were introduced later, the first choice would be batching embeddings in the indexer rather than scaling inference, because indexing is the only bulk workload.
